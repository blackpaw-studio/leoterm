# Leo Phase 3.5 — tmux Keystroke Forwarding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Forward host-surface keystrokes to the active tmux control-mode pane as `send-keys` commands, so a rendered agent cell becomes interactive (you can type into the agent), without racing the output-path `viewer.next()` and without infinite-looping on the viewer's own control writes.

**Architecture:** A surface running `tmux -CC` is a control-mode client whose stdin expects tmux *commands*, not raw keystrokes. Phase 3 already renders the pane and built `StreamHandler.tmuxViewerInput(.{ .keys = bytes })` (converts bytes → `send-keys` and sends it) + the resize back-path. The missing piece is routing user keystrokes to that helper **on the termio thread** (where `viewer.next()` already runs from the output path) and **distinguishably** from the viewer's own `send-keys`/handshake writes. We do this with: (1) a new `termio.Message.tmux_keys` mailbox variant carrying user key bytes; (2) a `tmux_control_mode: bool` notification pushed termio→Surface on viewer enter/exit, setting a Surface flag; (3) `Surface.keyCallback` routing encoded keystroke bytes through `tmux_keys` **only when that flag is set** — leaving the normal-typing path completely untouched otherwise; (4) the termio mailbox drain handling `tmux_keys` by calling `tmuxViewerInput(.{ .keys })` on the termio thread.

**Why this design (vs alternatives):** `viewer.next()` mutates a shared action arena and must never run concurrently; the only safe call thread is the termio/IO thread (where the output-path call lives). User keys originate on the UI thread, so they must cross to the termio thread as a mailbox message before reaching `viewer.next()`. A *dedicated* message variant (not the shared `write_small/stable/alloc`) is what distinguishes user keystrokes from the viewer's own control-command writes (which keep using `write_*` via `messageWriter`), preventing an infinite loop. Gating Surface on a flag means non-control-mode typing uses the unchanged `write_*` path — zero blast radius for normal terminal use.

**Tech Stack:** Zig (src/termio, src/apprt, src/Surface.zig), tmux control mode. macOS app build via Xcode 26.3.

**Scope (this increment): KEYSTROKES ONLY.** Paste, mouse reporting, and terminal query auto-responses during control mode are explicitly OUT OF SCOPE here (documented follow-ups in §Deferred). Keystrokes are the high-value interactive slice.

**Concurrency invariant (must hold after every task):** `viewer.next()` is only ever called on the termio/IO thread — from `dcsCommand` (output path) and from the `tmux_keys` drain arm (this plan). It is NEVER called from `Surface.keyCallback` (UI thread).

- [ ] **Step 2: Add the `tmux_keys` variant to `Message`**

In `src/termio/message.zig`, add after `write_alloc` (keep it an allocated buffer — keystrokes are infrequent, per-keystroke alloc is fine, and it sidesteps the `.stable` lifetime question):

```zig
/// User keystroke bytes to forward to an active tmux control-mode viewer.
/// Distinct from write_* so the drain can route these to the viewer
/// (as send-keys) without intercepting the viewer's own control writes.
tmux_keys: WriteReq.Alloc,
```

Add a constructor mirroring `writeReq` but forcing the alloc variant (so callers can build it from any byte slice):

```zig
/// Build a tmux_keys message by copying `data` into an allocated buffer.
pub fn tmuxKeys(alloc: Allocator, data: []const u8) !Message {
    return switch (try WriteReq.init(alloc, data)) {
        // Force allocation so the bytes outlive the UI-thread caller.
        .small => |v| Message{ .tmux_keys = try smallToAlloc(alloc, v) },
        .stable => |v| Message{ .tmux_keys = try stableToAlloc(alloc, v) },
        .alloc => |v| Message{ .tmux_keys = v },
    };
}
```

> The exact construction must match the real `WriteReq` API. If `WriteReq.init` can be told to always allocate, prefer that (simpler — drop the small/stable conversions). Read `MessageData`/`WriteReq.init` in this file and use the simplest correct way to get an owned `WriteReq.Alloc` from a `[]const u8`. The contract: `tmux_keys` owns its bytes and the drain frees them. If adding `Message` overflows the size assertion at ~105, adjust per how `write_alloc` already fits (it's the same `WriteReq.Alloc` payload, so it will fit).

- [ ] **Step 3: Add a `Termio` method that runs the viewer input on the termio thread**

In `src/termio/Termio.zig`, after `queueWrite` (~423):

```zig
/// Forward user keystroke bytes to the active tmux control-mode viewer.
/// MUST be called on the termio/IO thread (the mailbox-drain thread), so
/// viewer.next() is never concurrent with the output parse path.
pub fn tmuxKeys(self: *Termio, data: []const u8) !void {
    _ = try self.terminal_stream.handler.tmuxViewerInput(.{ .keys = data });
}
```

> Confirm `self.terminal_stream.handler` is the `StreamHandler` (it is — used by the resize push in `Termio.resize`). `tmuxViewerInput` returns `!bool` (true if a viewer consumed it); we ignore the bool here (if no viewer is active, the keys are simply dropped — see §Deferred for the transition-window note). Guard with `if (comptime StreamHandler.tmux_enabled)` if `Viewer.Input` doesn't resolve when tmux is disabled (mirror the `Termio.resize` guard added in Phase 3).

In `src/termio/Thread.zig` `drainMailbox`, add an arm next to the `write_alloc` arm (~346):

.tmux_keys => |v| {

## Task 4: Route keystrokes through `tmux_keys` when control mode is active

The behavior change: when `Surface.tmux_control_mode` is set, encoded keystroke bytes go to tmux instead of the local pty.

- [ ] **Step 2: Gate the dispatch on the flag**

Replace the keystroke dispatch (~2810) so that, when in control mode, the bytes are sent as `tmux_keys` instead:

```zig
if (self.tmux_control_mode) {
    // Control-mode client stdin expects tmux commands, not raw keys.
    // Hand the encoded bytes to termio as tmux_keys; the termio thread
    // converts them to `send-keys` for the active pane. This keeps
    // viewer.next() on the termio thread (never the UI thread).
    const bytes = write_req.slice(); // use the real accessor from Step 1
    self.queueIo(try .tmuxKeys(self.alloc, bytes), .unlocked); // match queueIo's Message arg + alloc
} else {
    self.queueIo(switch (write_req) {
        .small => |v| .{ .write_small = v },
        .stable => |v| .{ .write_stable = v },
        .alloc => |v| .{ .write_alloc = v },
    }, .unlocked);
}
```

> Adapt to reality: the exact way to get `bytes` from `write_req` (it's a `WriteReq` union — there may be a `.slice()` helper; if not, switch over it to get the slice), the allocator field on `Surface` (e.g. `self.alloc`), and `queueIo`'s expected argument. IMPORTANT: if `write_req` was itself `.alloc` (owns memory), make sure you don't leak it — `tmuxKeys` copies the bytes, so an original `.alloc` write_req must still be freed; check how the normal path's `.alloc` is freed (the drain frees `write_alloc`'s buffer; here you're NOT sending it, so free the original alloc after copying, or construct `tmuxKeys` to take ownership of an existing `.alloc` without copying). Prefer the zero-copy path: if `write_req == .alloc`, hand its buffer directly to `tmux_keys` (transfer ownership) instead of copying. Handle all three `write_req` variants without leaking.

## Deferred (explicit follow-ups, NOT in this increment)

- **Paste / clipboard during control mode** (`completeClipboardPaste` ~5907): currently stays on `write_*` → would go raw to the `-CC` client. Route paste through `tmux_keys` (or a `load-buffer`/`paste-buffer` tmux command) in a follow-up.
- **Mouse reporting during control mode** (`mouseReport` ~3699): same; forward as tmux mouse events or suppress.
- **Terminal query auto-responses during control mode** (host StreamHandler `messageWriter` → `write_*`): these go raw to the `-CC` client. In practice the host terminal generates few/none during control mode (the app's queries hit the pane terminal, not the host), but audit and, if any occur, route appropriately.
- **Transition windows:** a keystroke in the brief gap between viewer enter and the flag propagating could go to the local pty (raw to the `-CC` client); between exit and flag-clear, a keystroke could be dropped. Both are sub-perceptible windows at attach/detach. If they prove problematic, make the termio drain authoritative (decide by live `tmux_viewer` state) instead of (or in addition to) the Surface flag.
